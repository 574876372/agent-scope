## 一、整体结构

```
                ┌──────────────────────── 写入 ────────────────────────┐
上传文件 ──► 落盘 + 文档记录(uploading) ──► 异步事件 ──► 解析结构 ──► 结构化切片
                                                             │
                             MySQL 切片表 ◄── 批量向量化 ◄───┘
                             向量库(ES)   ◄──┘

                ┌──────────────────────── 查询 ────────────────────────┐
GENERIC 对话 ─┐
AGENTIC 工具 ─┼──► RetrievalPipeline ──► ①改写 ②向量+关键词召回 ③RRF融合
演练场 / 评估 ┘                          ④重排(可选) ⑤上下文扩展 ⑥组装来源
```

**核心原则：三个查询入口共用同一条检索流水线 `RetrievalPipeline`**，保证演练场看到的结果就是智能体实际拿到的结果。

模块分工（遵循项目分层 `web → biz → service → dao`）：

| 模块 | 与 RAG 相关的职责 |
|---|---|
| `agent-scope-rag-spring-boot-starter` | 与业务无关的基础能力：文档结构还原、结构化切片、批量向量化、向量库工厂 |
| `agent-scope-service` | 数据访问：切片 / 文档 / 知识库查询，关键词检索（全文索引） |
| `agent-scope-biz` | 流程编排：入库流水线、检索流水线、查询改写、重排、上下文扩展、对话注入 |
| `agent-scope-web` | 接口：上传、重新解析、演练场、评估 |

## 二、数据存在哪里

一个文档入库后，数据分布在四个地方：

| 位置 | 内容 | 关键字段 |
|---|---|---|
| 本地文件 | 原始文件，重新解析时从这里读 | 路径 `{agent.rag.upload-dir}/{kbId}/yyyy/MM/dd/{docId}.{ext}`，库里只存相对路径 |
| `t_knowledge_document` | 文档元数据与解析状态 | `status`（uploading / parsing / indexed / failed）、`char_count`、`chunk_count`、`error_message` |
| `t_knowledge_chunk` | 切片原文，**检索时的权威数据源** | `id`、`doc_id`、`chunk_index`、`content`、`section_path`、`chunk_type`；`content` 上有 ngram 全文索引 `ft_content` |
| 向量库（ES） | 切片向量 | 索引名 `agent_knowledge_{kbId}`（小写）；字段 `doc_id`、`chunk_id`（= 切片序号）、`content`、`vector` |

两者之间的关联：

- 向量库的 `doc_id + chunk_id` ↔ 切片表的 `doc_id + chunk_index`（检索时用这个对应关系回查切片表）。
- 切片表主键 `id` = 向量文档 id（由 docId、chunkId、正文内容计算得出），删除向量时按它定位。

## 三、写入流程

### 3.1 流程总览

```
POST /api/knowledge-base/document/upload?kbId=
  │
  ├─ KnowledgeController.uploadDoc
  └─ KnowledgeBizImpl.uploadAndIndexDocument           【同步，立即返回】
       1. 校验：RAG 已启用、文件非空、知识库存在
       2. KnowledgeFileStorage.store  → 文件落盘，得到相对路径
       3. 插入 t_knowledge_document，status = uploading
       4. 发布 DocumentIndexEvent(docId, userId)

DocumentIndexEventListener.onDocumentIndexEvent        【异步，ragExecutor 线程池】
  │  恢复 UserContext（事件里带着 userId），finally 中清理
  └─ doParseAndIndex(docId)
       1. status = parsing
       2. 清理旧数据（仅重新解析时有）
       3. 解析结构 + 结构化切片          parseChunks
       4. 批量向量化 + 写入向量库        writeVectors
       5. 切片写入 MySQL                saveChunks
       6. status = indexed（任一步异常 → failed + error_message）
```

线程池 `ragExecutor`：核心 4、最大 8、队列 100，队列满时由调用线程执行（CallerRunsPolicy）。

### 3.2 第 2 步：清理旧数据

```java
if (切片表里该文档已有切片) {
    ragKnowledgeProvider.removeDocumentVectors(kbId, docId);  // 删向量
}
knowledgeService.purgeChunksByDocId(docId);                   // 物理删除切片
```

- **先删向量、再删切片**：删向量要用切片表里的 id 逐条定位。
- **物理删除**而不是逻辑删除：切片主键由内容计算得出，内容不变时重新入库会得到相同主键，逻辑删除的旧行还在就会主键冲突。
- 新上传的文档没有旧切片，跳过删向量。IN_MEMORY 模式下删向量会丢弃整个知识库的内存库，没必要触发。

### 3.3 第 3 步：切片参数

`KbConfigResolver.chunkOptions(kb)` 按「知识库级配置 → 类型预设 → yml 全局默认」解析：

| 参数 | 知识库级字段 | 类型预设（`KbTypePreset`） | 全局默认 |
|---|---|---|---|
| 切片策略 | `chunk_strategy` | 通用 / 技术：SECTION；FAQ：QA；表格：TABLE_ROW | — |
| 切片大小 | `chunk_size` | 技术 1000、表格 800、其余不指定 | `agent.rag.chunk-size` = 512 |
| 重叠字符数 | `chunk_overlap` | 不指定 | `agent.rag.chunk-overlap` = 80，且不超过切片大小的一半 |
| 表格整体保留 | — | 仅技术文档为 true（上限放宽到 2 倍切片大小） | — |

### 3.4 第 3 步：文档结构还原（`DocumentStructureReader.read`）

把各种格式统一还原成三种**结构块** `DocBlock`：标题（带层级）、段落、表格（表头行 + 数据行，Markdown 管道格式）。

| 格式 | 处理方式 |
|---|---|
| `.md` | `#` 标题（兼容 `##标题` 缺空格）；`\|` 开头的连续行识别为表格，第二行是 `---` 分隔行时第一行为表头；围栏代码块整体算一个段落，里面的 `#` 和 `\|` 不识别 |
| `.txt` | 空行分段；依次尝试 UTF-8、GBK、ISO-8859-1 解码；单行短文本按编号推断标题（见下表） |
| `.docx` | Apache POI 读取：段落的大纲级别 → 样式名（Heading N / 标题 N / Title，沿样式继承链最多查 5 层）识别标题；Word 表格转管道格式，首行作表头；**全文没有样式标题时**退回编号推断 |
| `.xlsx` / `.xls` | 每个工作表输出「一级标题（表名）+ 一张表格」，首个非空行作表头；公式取计算结果 |
| 其他（pdf、pptx、doc…） | Tika 提取全文（不限长度）后按 txt 规则处理 |

编号推断标题的规则（只对 ≤ 40 字、且不以句号 / 逗号 / 冒号 / 问号等结尾的单行生效）：

| 格式 | 层级 |
|---|---|
| 第X章 / 第X篇 / 第X部分 | 1 |
| 第X节 | 2 |
| 一、 | 3 |
| （一） | 4 |
| 1.1 | 5 |
| 1.1.1 | 6（每多一级小数点加 1） |

单级的「1 xxx」「1. xxx」**不算标题**，它们在正文里通常是列表项，算作标题会把列表拆成大量碎片。

### 3.5 第 3 步：结构化切片（`StructuredChunker.chunk`）

输出 `ChunkPiece`：正文 `content`、章节路径 `sectionPath`（如「支付平台接口文档 › 三、独立代发 › 请求参数」）、切片类型 `chunkType`（text / table / qa）。

**SECTION（按章节）**，TABLE_ROW 与它共用同一套逻辑：

1. 维护一个**标题栈**：遇到标题时弹出所有层级 ≥ 它的旧标题再压入，栈内标题用「 › 」连起来就是章节路径。
2. 遇到新标题就结束当前切片，**切片不跨章节**。
3. 章节的第一片以章节标题作为首行，便于阅读和关键词命中。
4. 段落依次累积，放不下（超过切片大小）时输出当前切片、开始新切片。
5. 单个段落本身超长时按句拆分（句末标点 `。！？!?；;` 和换行），相邻片保留重叠；单句仍超长时硬切。
6. **表格**：
   - 表格前的缓冲文字 ≤ 200 字（如标题行 +「请求参数如下：」）时并入表格首片作为说明，否则先单独输出。
   - 说明 + 整张表在上限内 → 整表一片。
   - 超出 → 按行分组，**每组都重复表头**，任何一行都不会被切断；单行超长时独占一片。说明文字只出现在第一片。

**QA（一问一答）**：

1. 用正则识别问题行：`Q:`、`Q1.`、`问：`、`问题1：`、`【问题】`、以问号结尾的短句（2~80 字）。
2. 从一个问题到下一个问题之间是一组问答，成为一片；第一个问题之前的说明文字单独成片。
3. 识别出的问题**少于 2 个**时，说明不是问答格式，退回按章节切分。
4. 一组问答超过切片大小的 3 倍时按句拆分，每片都重复问题行。

### 3.6 第 4 步：批量向量化与写入向量库（`writeVectors`）

```
1. spec = RagKnowledgeProvider.resolveEmbeddingSpec(kbId)
      知识库绑定的向量模型 t_model → 厂商 t_model_provider → 解密 API Key
2. 每片的向量化文本 = EmbeddingTextBuilder.build(文档名, 章节路径, 正文)
      例：「接口文档 › 三、独立代发 › 请求参数\n| 12 | payeeName | ... |」
3. vectors = BatchEmbeddingClient.embedAll(spec, texts, batchSize)
      · 每批 agent.rag.embedding-batch-size 条（默认 10），一次 /embeddings 请求，input 为字符串数组
      · 某一批失败（厂商不支持数组输入）→ 这一批改为逐条请求，逐条仍失败才报错
      · 按返回的 index 还原顺序；返回维度与模型配置不一致时报错
4. 构造向量文档：docId、chunkId = 切片序号、content = 切片原文（注意：不含路径前缀）、embedding = 上一步的向量
5. store = getKnowledge(kbId).getEmbeddingStore()，每 200 条 add 一次
```

重点：**向量用「路径 + 正文」计算，但向量库和切片表里存的都是原文。** 这样「请求参数表的第 40 行」这种自身没有主题词的切片，也能被「代发接口请求参数」这样的问题检索到。

### 3.7 第 5、6 步：写切片表与收尾

- 切片表每行：`id` = 向量文档 id、`chunk_index` = 序号、`token_count` ≈ 字数 / 2（粗略估算）、`section_path`（超过 512 字截断）、`chunk_type`。
- 文档回写 `char_count`、`chunk_count`，状态改为 indexed。
- 任一步异常：状态改为 failed，`error_message` 写入原因（超过 500 字截断），前端鼠标悬停可见。

### 3.8 重新解析、删除

| 操作 | 接口 | 过程 |
|---|---|---|
| 文档重新解析 | `POST /api/knowledge-base/document/reparse?docId=` | 状态置 parsing，发布同一个 `DocumentIndexEvent`，后续与上传完全相同（第 2 步负责清理旧数据）；正在解析中的文档返回 409 |
| 知识库重新解析 | `POST /api/knowledge-base/reparse?kbId=` | 对每个不在解析中的文档执行上面的操作；前端按文档状态统计进度 |
| 删除文档 | `DELETE /api/knowledge-base/document/delete?docId=` | 删文件 → 删向量 → 逻辑删除切片 → 逻辑删除文档 |
| 删除知识库 | `DELETE /api/knowledge-base/delete?id=` | 记下绑定的智能体 → 解除绑定 → 逐个删除文档 → 释放向量库连接 → 删除评估用例 → 逻辑删除知识库 → 让这些智能体的运行时缓存失效 |

### 3.9 IN_MEMORY 模式的补充

开发时可以把向量库配成 `IN_MEMORY`。内存库不持久化，进程重启后是空的，所以 `RagKnowledgeProvider.getKnowledge` 发现内存库为空时，会**从切片表全量回灌**：用与入库相同的「路径 + 正文」规则批量重算向量。ES / Milvus 不走这段逻辑。

## 四、查询流程

### 4.1 三个入口

| 入口 | 触发 | 检索词 | 查询改写 | 结果去向 |
|---|---|---|---|---|
| **GENERIC 对话** | 每次用户发消息，调用智能体**之前** | 用户原话 | 按智能体配置（默认开） | 注入模型上下文 + SSE `retrieval` 事件 + 写入助手消息 |
| **AGENTIC 工具** | 模型自己决定调用 `retrieve_knowledge` 工具 | 模型给出的检索词 | 关闭（模型已经自己组织好了检索词） | 作为工具结果返回给模型 |
| **演练场** | 知识库页「检索演练」 | 输入的测试问题 | 可选，用默认对话模型 | 返回所有中间结果，分步展示 |
| （评估） | 知识库页「评估」→ 运行 | 用例问题 | 关闭 | 统计召回率 / 完整度 |

### 4.2 GENERIC 对话的完整过程

```
POST /api/chat/message/stream
  │
  └─ ChatBizImpl.sendMessageStream
       1. 带 hitlAction 的请求 → 转交审批流程（与 RAG 无关）
       2. resolveConversationId：没有会话则新建
       3. prepareStreamContext
            · 加载会话；关联的智能体已删除 → 报 410「智能体已删除」
            · 追加用户消息并先保存（保证提问不丢）
            · MemoryManager.resolveContext 按记忆模式裁剪历史
       4. buildAgentStreamFlux
            a. 推送控制帧 [CONV_ID]xxx
            b. retrieveForGeneric(会话, 问题)                 ◄── 检索发生在这里
                 · 智能体 rag_mode ≠ GENERIC 或没绑定知识库 → 跳过
                 · options = pipeline.agentOptions(智能体, 绑定的知识库)
                 · options.history = 本轮之前的全部 user / assistant 消息
                 · trace = RetrievalPipeline.run(options)
                 · 异常时只记日志，本轮不带知识库上下文继续对话
            c. chatRequest.knowledgeContext = trace.contextText
            d. 有来源段或告警时：
                 · 生成 JSON（问题、改写后问题、来源段、告警、耗时）
                 · 推送 SSE：event: retrieval
                 · 暂存到 StreamAccumulator，最后随回复一起保存
            e. AgentBizImpl.chatStream
                 · 取缓存的智能体实例（没有则构建）
                 · 清空记忆，写入裁剪后的历史（去掉 <retrieval> 块，不让来源 JSON 占上下文）
                 · 本轮输入 = [用户问题, 知识库上下文]，两条都是 user 消息
                 · 推送 reasoning / tool_result / message 事件
            f. 结束：保存助手消息
                 <retrieval>{来源JSON}</retrieval><think>推理</think>工具摘要 + 回复
               推送 [DONE]
```

知识库上下文只存在于本轮调用，**不写进会话历史**；下一轮提问会重新检索。

前端：`ChatMain` 收到 `retrieval` 事件后，在回答上方显示「引用了 N 个来源」折叠块（`RetrievalSources.vue`）。打开历史对话时，从消息开头的 `<retrieval>` 块解析出同样的内容（`parser.ts`）。

### 4.3 AGENTIC 模式的过程

```
构建智能体（AgentBizImpl.loadRagKnowledge）
  · 只有 rag_mode = AGENTIC 才注入
  · new EnhancedKnowledge(pipeline, 智能体级参数模板)  ── 一个实例覆盖全部绑定的知识库
  · builder.knowledges([它]).ragMode(AGENTIC)
  · 框架据此注册工具 retrieve_knowledge(query, limit)

对话中模型调用工具
  └─ KnowledgeRetrievalTools.retrieveKnowledge（框架代码）
       └─ EnhancedKnowledge.retrieve(query, config)       在 boundedElastic 线程池执行
            · 最终段数：智能体配置了就用智能体的，否则用工具传入的 limit（最多 10）
            · queryRewrite = false
            · trace = RetrievalPipeline.run(...)
            · 每个来源段转成一个 Document，正文为「[n] 来源：文档 › 章节 › 切片 #a-#b\n原文」
       └─ 框架拼成 "Retrieved N relevant document(s): Document 1 (Score: …): …" 返回给模型
```

构建智能体时**不会**访问向量模型，所以某个知识库缺 API Key 不会导致智能体构建失败，只会在检索时被跳过并告警。

### 4.4 检索流水线（`RetrievalPipeline.run`）

参数来源：`RetrievalOptions`，为空的项取 `agent.rag.retrieval.*` 全局默认。

#### ⓪ 加载知识库

按 ID 批量查询；不存在或已删除的记入告警并跳过。

#### ① 查询改写（`QueryRewriter`）

```
条件：开关开启（智能体配置 ?? 全局 query-rewrite=true）且有对话历史
历史：只取最近 history-turns × 2 条（默认 3 轮 = 6 条）
模型：智能体自己的对话模型；演练场没有智能体，用默认对话模型
提示词：
  system：你是查询改写助手……只输出改写后的一句问题……已经完整就原样输出
  user：  对话历史：
          用户：代发接口的请求参数
          助手：（去掉推理块、来源块、工具调用行，每条最多 300 字）
          最新问题：那响应参数呢？
调用：temperature=0，最多 200 token，超时 15 秒，不重试
清洗：只取第一行，去掉「改写后的问题：」这类前缀和引号；为空或过长视为无效
结果：「代发接口的响应参数有哪些」；失败或无效时沿用原问题并记告警
```

#### ② 两路召回

**向量召回（每个知识库一路）**

```
阈值 = 智能体配置 ?? agent.rag.default-score-threshold（0.3）
对每个知识库：
  knowledge = RagKnowledgeProvider.getKnowledge(kbId)     每次都查最新的模型配置
  问题向量：同一个 Embedding 模型实例只计算一次（多个知识库共用一个模型时省去重复请求）
  store.search(问题向量, limit = vector-top-n 20, scoreThreshold = 阈值)
  再过滤一次：相似度 < 阈值的丢弃
  按相似度降序排名（1 起）
  任何异常（模型停用、缺 Key、ES 不通）→ 记告警，跳过这个知识库
```

向量库只返回 `doc_id`、`chunk_id`、原文和分数，所以后面要回查切片表补全信息。

**关键词召回（跨知识库一路，`KeywordRetrieveServiceImpl`）**

```
a. 精确词：从问题里提取形如标识符的词
     规则：[A-Za-z0-9_]{4,64}，且（同时含字母和数字）或（含大写字母或下划线）
     例：partnerOutBizNo、BBLMAP00000 算；what、hello 不算
     最多取 3 个（越长越优先），每个词做一次 content LIKE '%词%'
     得分 = 1000 + 同一切片命中的精确词个数（保证排在全文结果前面）
b. 全文检索：MATCH(content) AGAINST(问题前 200 字 IN NATURAL LANGUAGE MODE)
     ngram 分词，按相关度排序；失败（比如全文索引还没建）只记告警
c. 两部分按切片 id 合并去重，按得分降序，截取 keyword-top-n（20）
```

**补全（hydrate）**

- 向量命中按 `(doc_id, chunk_index)` 批量回查切片表，补上切片 id、章节路径、切片类型和切片表里的原文。
- 所有命中补上文档名。**文档已被删除的命中直接丢弃**（向量库里残留的旧向量不会被用到）。
- 丢弃后重新编排名。

#### ③ RRF 融合（`RetrievalPipeline.fuse`）

```
路 = 每个知识库的向量结果各一路 + 关键词结果一路
每个切片的得分 = Σ 1 / (rrf-k + 它在各路中的排名)，rrf-k 默认 60
同一切片（doc_id + chunk_index）在多路出现时合并，得分相加
按得分降序
```

例：某切片向量排第 2、关键词排第 1 → 1/62 + 1/61 ≈ 0.0325；只在向量中排第 1 → 1/61 ≈ 0.0164。**两路都命中的切片会排到前面。**

#### ④ 重排（可选，`CohereCompatibleReranker`）

```
模型 = 智能体指定的 rerank_model_id ?? 默认重排模型（model_type=RERANK 且 is_default=1）
没有可用的重排模型 → 跳过，保持融合顺序
取融合结果前 rerank-candidates（30）个
POST {baseUrl}/rerank
  {model, query, documents:[切片原文…], top_n, return_documents:false}
← {results:[{index, relevance_score}]}
按 relevance_score 重排这 30 个，其余保持在后面
失败 → 记告警，保持融合顺序
```

#### ⑤ 上下文扩展（`ContextExpander.expand`）

参数：最终段数 Top-K（智能体 `recall_limit` ?? 5）、总字数上限（`context_max_chars` ?? 8000）、整章上限（`section-max-chars` 4000）。

**a. 计算每个命中的扩展范围**（按排名从高到低处理）

| 知识库类型 | 扩展规则 | 标记 |
|---|---|---|
| 技术 / 接口文档，且命中切片有章节路径 | 查同一章节的全部切片，总字数 ≤ min(4000, 总上限) → 整章 | section |
| 其他情况，窗口 w > 0 | [序号 − w, 序号 + w]；w 取知识库 `context_window` ?? 预设（通用 1、技术 2、表格 1） | window |
| FAQ（w = 0） | 只要命中切片本身 | none |

**b. 合并成段**

- 与同一文档中已有的段**重叠或相邻**时并入，范围取并集，记录命中的序号。
- 否则新建一段，但已有 Top-K 段时直接舍弃（排名更低的命中）。
- 段扩大后如果又和同文档的其他段相连，继续合并。

**c. 读取原文**

- 按范围从切片表读取切片，拼接成连续原文：
  - 与上一片末尾重叠 10~400 字的部分去掉（旧版固定长度切片带重叠）；
  - 拆分表格时每片重复的表头去掉。
- 范围超出文档末尾时，以实际读到的切片为准。
- 切片表里读不到时（旧数据），用命中切片自带的原文。

**d. 总字数预算**

```
按段内最佳排名从高到低依次纳入：
  放得下 → 纳入
  放不下 → 先收缩到只包含命中切片的范围（去掉扩展进来的相邻切片），标记 trimmed
  还放不下 → 排名第一的段截断并加「……（内容过长，已截断）」；其余段舍弃
```

**e. 排序与编号**

同一文档的段排在一起，按原文顺序；文档之间按其最佳排名排序。依次编号 [1] [2] …

#### ⑥ 组装上下文

```
<retrieved_knowledge>
以下是从知识库检索到的参考资料（共 3 段）。回答时优先依据这些资料，引用时在句末标注来源编号，如 [1]；
资料中没有的信息请明确说明未检索到，不要编造。

[1] 来源：接口文档.docx › 三、独立代发 › 请求参数 › 切片 #10-#14
（连续原文）

[2] 来源：……
</retrieved_knowledge>
```

同时返回 `RetrievalTrace`：原问题、改写后问题、各阶段命中（演练场才保留）、最终来源段、告警、各阶段耗时。

### 4.5 一次检索的外部调用次数

| 步骤 | 调用 | 次数 |
|---|---|---|
| 查询改写 | 对话模型 | 0 或 1 |
| 向量召回 | Embedding | 每个**不同的**向量模型 1 次 |
| 向量召回 | 向量库 search | 每个知识库 1 次 |
| 关键词召回 | MySQL | 精确词最多 3 次 LIKE + 1 次全文检索 |
| 补全 | MySQL | 切片 1 次 + 文档 1 次 |
| 重排 | 重排模型 | 0 或 1 |
| 扩展 | MySQL | 每段 1 次范围查询；技术文档每个章节再加 1 次 |

## 六、关键设计点（为什么这么做）

1. **向量用「路径 + 正文」计算，存储用原文**：表格中间行、列表后半段这类自身没有主题词的切片，靠章节路径获得语义；展示和注入模型的仍是干净的原文。
2. **两路召回 + 按排名融合**：向量检索对「partnerOutBizNo」「BBLMAP00000」这类精确词不敏感，关键词检索补上这一点。不同向量模型的分数分布差别很大，不能直接比较分数，所以只看排名。
3. **每个知识库单独算一路**：多个知识库可能绑定不同的向量模型，各自的第一名同等对待，避免某个知识库因为分数整体偏高而垄断结果。
4. **阈值只做预过滤**：阈值只用来去掉明显不相关的向量结果，最终排序不看它，所以阈值设得保守一点也不影响排序。
5. **命中后扩展而不是一味多召回**：召回 20 片再合并成少数几段连续原文，让模型看到完整的表格和上下文，解决「找到了但不全」的问题。
6. **GENERIC 由业务层检索，不用框架的 GenericRAGHook**：框架的 Hook 只用最后一句话检索，注入的内容里没有出处，也拿不到检索过程。自己做才能支持查询改写、来源标注和前端展示。
7. **切片表是权威数据源**：向量库只负责「找到是哪一片」，章节路径、切片类型、相邻切片都从切片表取。换向量库、重建向量都不影响这些信息。
8. **异常处处降级**：单个知识库失败、改写失败、全文检索失败、重排失败，都只记告警、继续执行，不会让对话中断。

## 七、已知局限

| 局限 | 影响 | 后续方向 |
|---|---|---|
| 精确词用 `LIKE '%词%'` | 知识库切片数很多（几十万级）时变慢 | 改为自建 ES 分词字段，或只用全文索引 |
| 知识库类型写死为 4 种、只能设在知识库级 | 新场景要改代码；混合文档的知识库部分文档切得不好 | 解析模板做成数据表，支持文档级覆盖 |
| 入库前不能预览切片 | 只能入库后在演练场检查 | 增加只解析不入库的预览接口 |
| QA、标题靠正则识别 | 格式不规范的文档识别不准 | 模板里可配置识别规则；支持问答两列直接导入 |
| 查询改写每次多一次模型调用 | 增加 0.5~2 秒延迟 | 可在智能体上关闭 |
| 本轮用户消息会发给模型两次（历史里一次、本轮输入一次） | 多占少量 token（原有问题，与 RAG 无关） | 待修复 |
| 没有文档元数据过滤 | 不能按版本、部门限定检索范围 | 文档标签 + 检索过滤 |
