## 一、背景与目标

### 1.1 触发问题

智能体绑定《支付平台-独立代发接口文档》后提问，回答能找到相关内容，但出现"请求参数序号 12~70 未检索到""字段长度被截断"等缺失。原因是检索送给模型的内容本身不完整，模型只能看到被召回的少数切片。

### 1.2 目标与验收标准

| 目标 | 验收方式 |
|---|---|
| 长表格、长章节能完整召回 | 问「独立代发接口的全部请求参数」，回答包含参数表全部行，不出现"未检索到""被截断" |
| 精确词能命中 | 问 `BBLMAP00000`、`partnerOutBizNo` 这类代码或字段名，能召回对应切片 |
| 多轮追问能检索 | 先问「代发接口的请求参数」，再问「那响应参数呢？」，第二问能召回响应参数 |
| 检索过程可见 | 回答区显示「引用来源：文档名 › 章节 › 切片范围」 |
| 演练场与实际一致 | 知识库演练场使用与智能体完全相同的检索逻辑，并分步展示中间结果 |
| 多类型文档适配 | 通用文档、FAQ、表格数据各选一份样例，按对应类型预设入库后检索结果合理 |

## 二、现状分析

### 2.1 当前链路

```
入库：上传 → AgentScope Reader 解析 → 固定长度切片（chunk-size 512，段落策略，重叠 80）
     → 逐片调用 Embedding → 写入向量库（ES）+ MySQL 切片表

检索：AgentScope GenericRAGHook 取用户最后一句话 → 各知识库向量检索 Top-K（默认 3）
     → 以 <retrieved_knowledge> 文本（仅含分数与正文）注入上下文
```

### 2.2 已核实的框架事实（AgentScope 1.0.11）

| 事实 | 对设计的影响 |
|---|---|
| `io.agentscope.core.rag.Knowledge` 是只有 `addDocuments`、`retrieve` 两个方法的接口 | 可自行实现增强检索器，无需修改框架 |
| `RetrieveConfig` 含 `limit`、`scoreThreshold`、`conversationHistory` | 检索参数可透传 |
| `GenericRAGHook` 用最后一条用户消息检索，注入内容只有 `Score` 与 `Content`，**没有文档名** | 模型无法标注出处；需要自行控制注入格式 |
| AGENTIC 模式由 `KnowledgeRetrievalTools.retrieveKnowledge` 作为工具暴露 | 底层换成增强检索器即可复用 |
| `ElasticsearchStore` 的正文字段存的是**序列化后的 ContentBlock JSON**，不是分词字段 | 无法直接在现有 ES 索引上做关键词检索 |

### 2.3 问题清单

| # | 问题 | 影响 | 处理 | 阶段 |
|---|---|---|---|---|
| 1 | 固定长度切片会**从表格行中间切断**，后续切片丢失表头 | 表格残缺，中间切片难以被检索到 | 结构化切片（5.1） | P2 |
| 2 | 默认只召回 3 片，且**只返回命中片本身** | 找到了但补不全 | 召回后上下文扩展（6.5） | P1 |
| 3 | **只有向量检索** | 字段名、错误码、条款号等精确词易漏 | 增加关键词召回并融合（6.2、6.3） | P1 |
| 4 | GENERIC **只用最后一句话检索** | 追问类问题检索不到 | 结合对话历史改写检索词（6.1） | P2 |
| 5 | 注入内容**无来源**，界面看不到检索过程 | 无法标注出处，无法判断知识库是否生效 | GENERIC 检索改由业务层执行并推送来源（第七节） | P1 |
| 6 | 切片参数**全局一套** | 不同文档的最佳切法不同 | 知识库类型预设 + 知识库级配置（第四节） | P2 |
| 7 | 多个知识库**共用相似度阈值** | 不同向量模型分数分布不同，阈值无法通用 | 融合按排名，阈值仅作向量预过滤（6.3） | P1 |
| 8 | 改切片参数后**无法重新解析** | 只能删除后重新上传 | 文档级、知识库级重新解析（5.4） | P2 |
| 9 | 向量化**逐片调用 HTTP** | 大文档入库慢 | 批量向量化（5.5） | P2 |
| 10 | 删除知识库后**已缓存的智能体仍持有它** | 重启前持续查询已删除数据 | 删除知识库时使智能体缓存失效 | P0 |
| 11 | **单个知识库出错导致整个智能体不可用** | 如向量模型缺 API Key 时无法对话 | 按知识库隔离异常，跳过并告警 | P0 |
| 12 | 删除智能体后**对话残留且可继续发消息** | 报「Agent 不存在」 | 删除智能体时处理其对话【待确认】 | P0 |
| 13 | 会话列表接口**不返回 agentId** | 前端无法显示对话所属智能体 | 接口补字段 | P0 |
| 14 | 前端**无编辑智能体入口** | 调整检索参数只能删除重建 | 新增编辑功能 | P0 |
| 15 | 创建智能体**默认勾选全部工具** | 不需要的工具被调用 | 默认仅勾选 `agent.tool.default-enabled` | P0 |
| 16 | 模型输出 `##标题` 缺空格时**不渲染为标题** | 显示为 `##四、` | 前端渲染前补空格 | P0 |

## 三、目标架构

### 3.1 链路总览

```
【入库链路】
上传文件 → 解析文本（AgentScope Reader；Word 读取标题样式）
        → 按知识库类型切片（StructuredChunker）
        → 每片记录章节路径，如「接口文档 › 三、独立代发 › 请求参数」
        → 向量化时正文前拼接章节路径（批量调用）
        → 写入向量库 + MySQL 切片表（章节路径、切片类型、序号）

【检索链路】EnhancedKnowledge（一个智能体一个实例，覆盖其绑定的全部知识库）
用户问题
  ① 查询改写（可选）：结合最近几轮对话改写为独立的检索词
  ② 两路召回：向量检索（每库用自己绑定的向量模型）+ 关键词检索（MySQL ngram 全文索引）
  ③ RRF 融合：按排名合并，不依赖各路原始分数
  ④ 重排序（可选）：配置了重排模型时启用
  ⑤ 上下文扩展：按知识库类型规则补充相邻片或整章，合并为连续原文，受总长度上限约束
  ⑥ 组装：每段标注「来源：文档名 › 章节 › 切片 #3-#6」
```

### 3.2 关键设计决定

1. **自行实现 `EnhancedKnowledge`**（实现 AgentScope 的 `Knowledge` 接口）。每个智能体只向 `ReActAgent.Builder#knowledges` 传入一个实例，多知识库检索与融合在其内部完成。
2. **GENERIC 模式的检索由业务层执行**，不再使用 `GenericRAGHook`。业务层在调用智能体前完成检索、注入上下文，并通过 SSE 推送引用来源。
3. **AGENTIC 模式**继续使用框架的检索工具，底层换成 `EnhancedKnowledge`，工具返回内容带来源。
4. **检索参数跟随知识库类型**，智能体级只保留与内容无关的参数（见第八节）。

### 3.3 新增与改动的主要类

| 类 / 文件 | 模块 | 说明 |
|---|---|---|
| `EnhancedKnowledge` | biz/rag | 实现 `Knowledge`，编排 ①~⑥ |
| `RetrievalPipeline` | biz/rag | 可单独调用的检索流水线，供 GENERIC、AGENTIC、演练场共用，返回各阶段中间结果 |
| `KeywordRetriever` | service | 基于切片表全文索引的关键词召回 |
| `ContextExpander` | biz/rag | 按知识库类型规则扩展上下文 |
| `QueryRewriter` | biz/rag | 结合对话历史改写检索词 |
| `Reranker`（接口）+ `CohereCompatibleReranker` | biz/rag | 调用 `/v1/rerank` |
| `StructuredChunker` | rag starter | 结构化切片 |
| `KbTypePreset`（枚举） | common | 知识库类型预设 |
| `RagKnowledgeProvider` | biz/rag | 改为构建 `EnhancedKnowledge`，按知识库隔离异常 |
| `DocumentIndexEventListener` | biz/event | 改用 `StructuredChunker`、批量向量化 |
| `ChatBizImpl` | biz | GENERIC 模式前置检索、推送 `retrieval` 事件 |

## 四、知识库类型预设

创建知识库时选择类型，自动带出切片与扩展参数；创建后可微调，修改后需重新解析。

| 类型 | 切片方式 | 上下文扩展 | 典型内容 |
|---|---|---|---|
| **通用文档**（默认） | 按标题章节切分，章节内按段落累积至 `chunk_size` | 前后各 1 片 | 制度规范、产品手册、方案、会议纪要 |
| **技术 / 接口文档** | 按章节切分；表格整体保留，超长时按行拆分且**每片重复表头** | 所在章节总长 ≤ 上限时整章带入，否则前后各 2 片 | 接口文档、数据字典 |
| **问答 FAQ** | 一问一答为一片 | **不扩展** | 客服问答、常见问题 |
| **表格数据** | 按行分组，每组重复表头 | 前后各 1 片 | Excel 清单、配置表 |

扩展规则通用约束：所有扩展结果受「上下文总长度上限」约束，超出时按融合排名从低到高舍弃。

## 五、入库链路改造

### 5.1 结构化切片（`StructuredChunker`）

| 文件类型 | 规则 |
|---|---|
| Markdown | 按 `#` 标题层级识别章节；章节内按段落组装，不超过 `chunk_size`；表格作为整体，超长按行拆分并重复表头，**不从行中间切断** |
| TXT | 按空行分段，段落累积至 `chunk_size` |
| Word（.docx） | 读取段落样式识别标题层级（Apache POI），其余同 Markdown |
| PDF、Excel、PPT 等 | AgentScope Reader 提取纯文本后按段落规则处理；Excel 按表格数据类型处理 |

每个切片记录：`section_path`（章节路径）、`chunk_type`（`text` / `table` / `qa`）、`chunk_index`（文档内序号）。

### 5.2 章节路径增强

向量化时使用「章节路径 + 换行 + 正文」计算向量，提升无标题切片（如表格中间行）的命中率；数据库与展示仍保存原始正文。

### 5.3 知识库级切片配置

`t_knowledge_base` 增加类型与切片参数（见第八节），为空时使用类型预设，预设缺省时使用 yml 全局默认。

### 5.4 重新解析

- 文档级：删除该文档旧切片与旧向量，按当前配置重新入库。
- 知识库级：依次重新解析该知识库全部文档，前端显示进度。
- 原文件保留在上传目录，无需重新上传。

### 5.5 批量向量化

每批 10~25 片调用一次 Embedding 接口（OpenAI 兼容协议支持数组输入），算好的向量直接写入向量库，不再经由 `SimpleKnowledge` 逐片计算。

## 六、检索链路改造

| 步骤 | 做法 | 默认值 |
|---|---|---|
| 6.1 查询改写 | 用智能体自己的对话模型，结合最近 3 轮对话改写为独立检索词；增加约 0.5~2 秒延迟 | 智能体级开关，默认开启【待确认】 |
| 6.2 向量召回 | 每个知识库单独检索，相似度阈值作为预过滤 | 每库 20 片 |
| 6.2 关键词召回 | 切片表 `content` 建 `FULLTEXT ... WITH PARSER ngram` 索引，与向量库类型无关【待确认】 | 20 片 |
| 6.3 RRF 融合 | 每片得分 = Σ 1 / (60 + 该片在各路结果中的排名) | — |
| 6.4 重排序 | 配置重排模型时对融合结果重排 | 默认关闭 |
| 6.5 上下文扩展 | 按知识库类型规则（第四节），同一文档相连切片合并为连续原文 | 最终 Top-K = 5 段，总长 ≤ 8000 字 |
| 6.6 组装 | 按来源分段标注，保持原文顺序 | — |

**重排模型接入**：模型管理新增 `RERANK` 类型，采用 Cohere / Jina 兼容的 `/v1/rerank` 请求格式（硅基流动 bge-reranker、本地 Xinference / TEI 部署可用）；通义 gte-rerank 为私有格式，后续适配。

**异常隔离**：单个知识库检索失败（模型停用、缺 API Key、向量库不可用）时记录告警并跳过，其余知识库结果正常返回。

## 七、检索可见性与引用来源

- 后端新增 SSE 事件 `retrieval`：改写后的检索词；每个来源的文档名、章节路径、切片范围、融合得分。
- 该信息作为独立内容段写入助手消息，历史对话中同样可见。
- 前端在回答上方显示折叠块「引用了 N 个来源」，展开查看片段原文。
- 知识库演练场调用同一 `RetrievalPipeline`，分步展示：改写检索词 → 向量命中 → 关键词命中 → 融合结果 → 扩展后最终上下文。

## 八、配置与数据库变更

### 8.1 配置层级

| 配置 | 全局默认（yml） | 知识库级 | 智能体级 |
|---|---|---|---|
| 知识库类型 | — | ✓ | — |
| 切片策略、大小、重叠 | ✓ | ✓ | — |
| 上下文扩展规则 | ✓（按类型预设） | ✓ | — |
| 每路召回数 | ✓ | — | — |
| 最终段数 Top-K、上下文总长上限 | ✓ | — | ✓ |
| 向量预过滤阈值 | ✓ | — | ✓ |
| 查询改写开关 | ✓ | — | ✓ |
| 重排模型 | ✓（默认重排模型） | — | ✓ |

### 8.2 yml 示例

```yaml
agent:
  rag:
    chunk-size: 512                  # 类型预设未指定时的兜底
    retrieval:
      vector-top-n: 20               # 每个知识库向量召回数
      keyword-top-n: 20              # 关键词召回数
      rrf-k: 60
      final-top-k: 5                 # 最终交给模型的段数
      context-max-chars: 8000        # 注入上下文总长上限
      query-rewrite: true
      history-turns: 3               # 查询改写参考的对话轮数
```

### 8.3 数据库变更（均为新增）

| 表 | 变更 |
|---|---|
| `t_knowledge_base` | 新增 `kb_type`、`chunk_strategy`、`chunk_size`、`chunk_overlap`、`context_window` |
| `t_knowledge_chunk` | 新增 `section_path`、`chunk_type`；`content` 建 ngram 全文索引 |
| `t_agent_info` | 新增 `query_rewrite`、`context_max_chars`、`rerank_model_id` |
| `t_model` | `model_type` 增加取值 `RERANK`（结构不变） |

存量数据：已入库文档无章节路径，检索照常可用，上下文扩展退化为前后相邻片；执行一次重新解析即可获得全部能力。

## 十、适用范围与边界

| 文档类型 | 适配程度 | 说明 |
|---|---|---|
| 规章制度、流程规范 | ✅ | 章节切片 + 章节路径效果好；条款号依赖关键词召回 |
| 产品手册、操作指南 | ✅ | 步骤类内容依赖相邻片扩展 |
| 技术方案、接口文档 | ✅ | 使用「技术 / 接口文档」类型 |
| 合同、法律条款 | ✅ | 条款编号依赖关键词召回 |
| FAQ 问答对 | ✅ | 使用「问答 FAQ」类型，不做扩展 |
| Excel 数据表 | ✅ | 使用「表格数据」类型；受总长上限约束 |
| 会议纪要、长篇叙述 | ✅ | 通用文档类型即可 |
| Word 文档 | ✅（P2 起） | 依赖标题样式识别 |
| 扫描版 PDF、图片 | ❌ 不在本次范围 | 需要 OCR 能力，另行规划 |
| 统计、计算类需求 | ❌ 不适合 RAG | 如"上月各门店销售额合计"。应导入数据库，使用项目已有的 SQL 查询智能体（数据源功能） |

## 十一、风险与取舍

| 事项 | 说明 |
|---|---|
| 查询改写增加延迟与费用 | 每次提问多一次模型调用；做成可关闭开关，演练场可对比开关效果 |
| MySQL ngram 全文检索的规模上限 | 适合几十万片以内；数据量更大时改为自实现 ES 存储、使用分词字段与原生 BM25 |
| 不再使用 `GenericRAGHook` | 升级 AgentScope 时该部分不会自动获得框架改进；换来来源展示、历史感知检索与注入格式可控 |
| 存量数据能力受限 | 需重新解析才能获得章节路径与结构化切片 |
